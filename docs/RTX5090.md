# RTX 5090 / Blackwell (sm_120) optimization profile

This document explains how the crate targets the GeForce RTX 5090 (GB202, compute capability
12.0): the public specs the model uses, the occupancy model, the autotuner, the NVRTC sm_120
build, and a roofline with **projected** numbers.

> **Nothing in this document is a measurement on an RTX 5090.** The development machine has no
> GPU. Every number below is either a public spec (with a source) or a projection computed by
> `cargo run --release --bin roofline` from those specs and the stated assumptions. Real numbers
> come from `scripts/bench.sh` on real hardware, which now autotunes and records results in
> `results/<date>-<gpu>-autotune.{md,csv}`.

Notes on disagreements between sources:

* **Blocks per SM**: the Programming Guide table lists 24 for 12.x, the Blackwell Tuning Guide
  says 32. `tuning::SM120_RTX5090` uses 24 (conservative). It only matters for 1-warp blocks.
* **Shared memory per SM**: the Tuning Guide says 128 KB capacity per SM, the Programming Guide
  says 100 KB maximum shared memory per SM; per block both say 99 KB. The model uses 100 / 99.
* **INT32 throughput**: whitepaper v1.1 says many INT ops run at up to 2x Ada; developer-forum
  reports dispute that `IMAD`-class ops reach 2x. The compute roof therefore uses the
  conservative 64 INT32 lanes per SM; an optimistic roof would halve every `t_int` below.

## 2. What is tuned and why it matters on sm_120

The W2A8 kernels have three knobs: **warps per block** (1, 2, 4, 8), **rows per warp** (1, 2, 4:
how many output rows each warp keeps in registers, reusing every activation load R times) and
**split vs fused** (quantize + GEMV as two launches, or one launch with quantization in the
prologue, which re-reads the fp16 activations per block).

sm_120 specifics that drive the choice:

* **48 warps per SM** (vs 64 on sm_80/sm_90) and 64K registers: the `b16_r4` kernel uses 204
  registers per thread, so only 2 blocks of 4 warps fit (8 warps/SM). Register pressure, not
  shared memory, is usually the occupancy limiter.
* **99 KB shared per block** after the opt-in: the fused kernel fits `batch * K <= ~98 KB`
  (e.g. batch 16 at K = 6144), so it covers every BitNet-2B decode shape up to batch 14 at
  K = 6912.
* **170 SMs**: a 640-row projection (k/v) with 4 rows per warp and 4 warps per block is only 40
  blocks, a quarter of the GPU; smaller blocks win there.
* **1792 GB/s with ~600 ns DRAM latency** (assumed) needs ~6.3 KB in flight per SM (Little's
  law). Each warp keeps 512 B per row in flight (one 16-byte `uint4` per lane), so this is met
  with roughly 12 warp-rows per SM.
* **96 MB L2** holds an entire BitNet-2B **block** (17.4 MB of 2-bit weights) and a looped
  transformer's whole weight set; see `docs/LOOPED.md`.

## 3. Occupancy model and autotuner

`ternary_gemm::tuning` (no GPU needed):

* `occupancy(spec, warps, regs, smem)`: CUDA-occupancy-calculator rules (256-register warp
  allocation granularity, 1 KB runtime smem reservation per block), returning blocks/SM and
  the limiting resource.
* `SM120_I8_REGS` / `SM120_I8_FUSED_REGS`: ptxas register counts of every kernel variant for
  sm_120. `tests/nvrtc_sm120.rs` re-assembles the PTX with ptxas and fails if the table drifts.
* `model_config` / `rank_configs`: a modelled time per config: weight bytes / bandwidth, plus
  activation re-reads per block from L2, divided by Little's-law latency coverage and SM
  coverage / tail efficiency, plus one extra launch for the split path. It is a **ranking
  heuristic**: it prunes 24 configs to a handful, it is not a prediction to quote.

`ternary_gemm::autotune::Autotuner` (feature `cuda`, needs a GPU):

1. Picks the profile for the device's compute capability (`profile_for`), with the device's real
   SM count and fused smem limit.
2. Times the model's top-N configs **plus the library default** with CUDA events (median of
   reps; quantization included for both split and fused, so they compare fairly). Including the
   default means a tuned result is never slower than untuned, up to timing noise.
3. Caches winners per `(N, K, batch)`, saves / loads a CSV keyed by device name.

`cargo run --release --bin autotune` tunes the BitNet-2B decode shapes and writes a Markdown
report with the measured best / default times, driver-reported registers, the model's
occupancy for the winner, and the roofline projection side by side. `scripts/bench.sh` runs it
on every GPU it benchmarks; on sm_120 it notes that Blackwell results were recorded.

## 4. NVRTC for sm_120

`Gpu::new` compiles for the device's exact `compute_XY` first (so `compute_120` on a 5090),
falling back to older PTX targets when the installed NVRTC is too old (the driver then JITs the
PTX forward). CI's `nvrtc` job compiles for `compute_80/86/89/90/120/120a` with NVRTC 12.8 from
NVIDIA's pip wheels, assembles each with ptxas, reports registers / spills, and runs
`tests/nvrtc_sm120.rs` (every tunable kernel exists for `compute_120` and `compute_120a`, and
the register table matches). Latest local result: 55 kernels per arch, **0 spills on sm_120**.

## 5. Roofline (projections)

Model: a W2A8 GEMV reads `N*K/4` bytes of packed weights + `4N` bytes of scales + `batch*K`
activation bytes once. `t_dram = bytes / 1792 GB/s`. Compute roof (an assumption): one `dp4a`
= 4 MACs at 64 INT32 lanes/SM/clock, with about one extra integer op per `dp4a` to decode
2-bit codes, so `MAC/s = 170 * 64 * 2.407e9 * 2`. Decode at batch 1-4 is DRAM bound; around
batch 8-16 the integer roof takes over under this assumption, which is why rows per warp
(register reuse of activations) and the INT32 question above matter at larger batch.

Other profiles: GeForce RTX 5090, H100 SXM5 80GB, GeForce RTX 4090, GeForce RTX 3090, A100 SXM4 40GB

How to read this against measurements: the 30-layer projection (~293 us per token step at
batch 1, i.e. ~3400 tokens/s for the ternary GEMVs alone) is an **upper bound** on what any
kernel could reach if it streamed weights at the full spec bandwidth; it ignores attention,
norms, launch overhead and the gap between achieved and spec bandwidth (achieved is always
lower; measure it). Use `results/*-autotune.md` from a real 5090 for actual numbers.

## 6. Reproducing on a real RTX 5090

```bash
./scripts/bench.sh            # builds, runs GPU correctness tests, benchmarks, autotunes
# or only the tuner:
cargo run --release --bin autotune -- --out results/$(date +%Y%m%d)-rtx5090-autotune \
    --cache results/tune-cache.csv
```

Requirements: driver >= 570 (Blackwell), CUDA 12.8+ NVRTC (bench.sh can pip-install it).
